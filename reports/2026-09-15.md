## dascore#927 — offsets de zona horaria rechazados por error

CodeRabbit re-revisó a las 23:52 del 14-sep, cinco minutos después del push de
ayer, y dejó **un hallazgo inline** (Major) en `dascore/utils/time.py:150`. Era
cierto, y el bug lo introducía nuestro propio código.

### El fallo

`_check_ns_strings` compara el valor en nanosegundos contra los segundos enteros
del mismo string para detectar un wrap silencioso. Esos segundos salían de
partir el string por el primer `"."`:

```python
heads = np.strings.partition(np.asarray(strings, dtype=str), ".")[0]
```

Con fracción **y** offset de zona, esa partición se lleva el offset por delante:
`"2020-01-01T00:00:00.123456789+01:00"` deja `"2020-01-01T00:00:00"`. Numpy sí
aplica el offset al valor en nanosegundos (lo normaliza a UTC), de modo que los
dos lados dejaban de coincidir, se marcaba `wrapped` y una fecha perfectamente
válida terminaba en `TimeOverflowError`.

Reproducido con numpy 2.5.3 y pandas 3.0.5, escalar y array:

| Entrada | Antes | Ahora |
| --- | --- | --- |
| `2020-01-01T00:00:00.123456789+01:00` | `TimeOverflowError` | `2019-12-31T23:00:00.123456789` |
| `2020-01-01T00:00:00.123456789-05:00` | `TimeOverflowError` | `2020-01-01T05:00:00.123456789` |
| `2020-01-01T00:00:00.123456789Z` | OK | OK |
| `2020-01-01T00:00:00.123+01:00` | OK | OK |

Solo afectaba a 7-9 dígitos fraccionarios: con menos, numpy infiere `ms`/`us` y
`_check_ns_strings` ya retornaba temprano. Con `Z` o `+00:00` no hay desfase, así
que los dos lados coincidían por casualidad.

### El arreglo

Se parsea el string completo con la unidad de segundos explícita, que conserva el
offset y tampoco puede wrapear:

```python
seconds = np.asarray(strings, dtype=str).astype("datetime64[s]")
```

El rango contra el que se valida pasa a ser el de UTC, que es el correcto en los
dos sentidos: un offset puede sacar del rango a una fecha que escrita cabía, y
puede meter en el rango a una que escrita no cabía.
